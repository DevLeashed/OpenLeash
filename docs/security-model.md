# Security model

Back to the [README](../README.md). To *report* a vulnerability, see [`SECURITY.md`](../SECURITY.md).

OpenLeash does not load arbitrary runtime mods: trusted mod code with filesystem or shell access would inherit the desktop application's authority, and the permission layer is not a sandbox. There is no safe plugin trust model that makes arbitrary in-process code harmless. Editing OpenLeash harness source files with the agent changes repository files on disk and takes effect only through the normal rebuild/restart; this is not runtime in-process modification.


**It runs arbitrary commands.** The `bash` tool passes the model's command string to a real shell (`-c` for bash or PowerShell). Nothing sandboxes it. New installs and settings files with no permission mode recorded start at **Full Access**, which runs tools and commands without asking; choose a more restrictive default in Settings → Permissions if that is not what you want. The deny rules and plan mode still apply.

**Reads are not sandboxed.** The permission check has an `inside()` guard for *write* paths and never applies it to reads. An absolute path given to `read_file` is used verbatim, so the agent can read anything your user account can — `~/.ssh/id_rsa`, `~/.aws/credentials`, browser profile databases. No prompt, no audit entry. This is inherent to a coding agent with a `read` tool, but it is a real limit of the sandbox, not an oversight.

The browser network policy is enforced by per-session CDP interception and a local
filtering proxy that pins DNS answers before connecting. `localhost` and loopback
remain usable for dev servers (except the protected debugging/proxy ports); LAN
hosts require `browser:lan <host>` approval; metadata, link-local, reserved and
browser-internal targets are blocked. `file://` is scoped to the project and
browser downloads. The proxy and CDP layer cover navigation, redirects,
subresources, popups, iframes, workers and service-worker traffic; Chromium is
launched with loopback proxy bypass disabled, QUIC disabled and non-proxied
WebRTC UDP disabled.

This is browser-specific network protection, **not** an OS sandbox or general
firewall. It does not constrain arbitrary processes; Chromium and OS bugs remain
outside the model. Page content, JS results, DOM snapshots and console/network
output are untrusted data. Sensitive interactions ask by default. A persistent
OpenLeash profile is opt-in and may let the agent act as you on sites you sign in
to there; it is a separate profile, never imported from your everyday browser,
and plaintext local data. See [Configuration](configuration.md#browser).

**`web_fetch` only reaches the public internet.** It is a read-only tool, so it runs without a prompt, which would otherwise make it a way to read anything the machine can reach. Loopback, private ranges (10/8, 172.16/12, 192.168/16), link-local, CGNAT, bare intranet hostnames and cloud metadata endpoints (`169.254.169.254`, `metadata.google.internal`) are refused, in IPv4 and IPv6 alike. A hostname that only *resolves* to a private address still gets through — blocking that without a TOCTOU race needs resolution-time checks — so this is a meaningful boundary, not a complete one.

## Browser plugin

**On by default does not mean unrestricted.** The browser is a separate Chromium
process/profile, not the app webview or your everyday browser. It starts lazily on
first use. By default the profile is throwaway. **Keep sign-ins between chats**
opts into an OpenLeash-owned persistent profile: the agent can then act as you on
sites you sign into there. It is not encrypted credential storage or a sandbox;
anything running as your user can read its files. No credentials are imported
from your real Chrome/Edge profile.

Page interactions (including arbitrary `js`) are permission-gated. `js` is not a
read-only escape hatch: use `read`, `snapshot` or `query` to inspect pages without
interacting. Submit/pay/buy/delete/transfer targets, password/payment fields and
uploads receive sensitive-action checks. Sensitive interactions ask even on Full
Access unless that site has an explicit `browser:site <host>` allow rule.
`browser:ask <host>` forces a prompt; deny rules win. Plan mode and read-only
subagents cannot interact. Raw `cdp` requires Developer mode and asks on **every**
call; there is no always-allow grant for it.

The browser network policy is deliberately different from `web_fetch`: local dev
servers are a core use case, so loopback is allowed, but LAN access needs approval.

| Target | Browser policy |
|---|---|
| Public HTTP(S)/WebSocket hosts | Allowed; the resolved addresses are checked too. |
| `localhost`, `*.localhost`, 127/8, `::1` | Allowed, except the harness's CDP/proxy ports. |
| RFC1918, CGNAT (including Tailscale), IPv6 ULA/site-local, `.local`, `.internal`, other intranet suffixes and single-label names | Per-host approval (`browser:lan <host>`). Public names resolving to loopback also need this approval. |
| Link-local 169.254/16 and fe80::/10; AWS `fd00:ec2::254`; Alibaba `100.100.100.200`; metadata names; unspecified, multicast, reserved and documentation ranges | Always blocked, including alternate decimal/hex/octal IPv4 and IPv4-embedded IPv6 forms. |
| `file://` | Only canonical paths within the project or the browser download directory; no UNC shares. |
| Browser-internal schemes (`chrome:`, `devtools:`, extensions, etc.) | Blocked. |

The pure classifier intentionally treats 198.18/15 as public because fake-IP
proxies use it for all DNS responses. This is a compatibility exception, not a
claim that benchmarking addresses are globally routed.

Enforcement combines CDP request interception with a local filtering HTTP proxy.
The proxy checks every DNS answer and connects to the checked IP, rather than
letting Chromium resolve the hostname again, to resist DNS rebinding. Chromium is
configured to route loopback through it too, disable QUIC and disable non-proxied
WebRTC UDP. This is browser-specific network control, **not an OS firewall**:
raw developer CDP, browser implementation bugs and protocols outside the controlled
HTTP(S) path must not be treated as a general network sandbox. See the source and
regression tests for exact range handling and platform limitations.

Browser text, DOM snapshots, console/network output and script results are
**untrusted page content**, not instructions or permission grants. Network logs
redact credential headers. Cookie inspection is limited to the current origin;
HTTP-only values are not exposed. Downloads use bounded, sanitised filenames in
the chosen download folder. Uploads ask, must resolve inside the project after
canonicalisation, and refuse environment files and `.git` internals.

The shared Browser view is an explicit **user-control** surface: your clicks,
typing and dialog answers act immediately, independently of agent approvals.
Annotate sends only when you press **Send to agent**, as an ordinary chat turn with
screenshot crops; comments, selectors and page text remain quoted data. Inline
style previews change the live page only, not project files.

**The allowlist is narrower than it looks.** Allow rules are prefix patterns (`npm test *`), and a rule is refused whenever the command *chains* — `&&`, `||`, `;`, `|`, a bare `&`, a newline, a redirect, `$(...)` or a backtick all fall outside the rule and need their own approval. Two things still to keep in mind: `git push *` also matches `git push --force origin main`, and the approval card shows the exact pattern, so what you grant is what you see. Treat a rule as "this program, with these arguments", not as a boundary.

**Read-only auto-approval is an allowlist, not a denylist** — a command runs without asking only if *every* segment is a known read-only command, so unknown commands prompt rather than run. The read-only list is also screened for arguments that can write or spawn (`find -fprintf`, `sort -o`, `git diff --output`, `env <command>`), since a first-token allowlist cannot express "does not write".

**Your project can talk to the agent — but only if you have trusted it.** If the project you open has an `OPENLEASH.md`, `AGENTS.md`, `CLAUDE.md` or `.openleash/instructions.md` **in its root**, the contents are injected into the system prompt of every agent working in that project, with instructions that they override the user's other guidance — capped at 40,000 characters each. The file is read from the project root only: there is no upward search, no reading of a parent directory, and no other project is affected.

The control is **folder trust**, and it fails closed. Every folder is untrusted until you decide otherwise, and an untrusted folder contributes **nothing** to the agent: none of its instruction files, none of its skills (`.openleash/skills`, `.claude/skills`), none of its project subagents (`.openleash/agents`), none of its hooks (`.openleash/hooks.json`) and none of its project MCP config (`.mcp.json`). So cloning an untrusted repository and opening it cannot plant instructions in the agent you then point at it. Before you decide, a dialog scans the folder and shows exactly what trusting it would load — each instruction file with its size and a preview, skills, subagents, hooks, MCP servers and any project setting override that would loosen the permission gate — and asks once whether to trust this folder or don't trust it. Either answer is remembered for that folder; dismissing the dialog records don't trust. There are no ongoing trust badges, parent-folder choices, or trust-level controls in Settings. Previously saved parent-folder decisions remain respected for compatibility. Nothing in this paragraph applies to `~/.openleash/OPENLEASH.md` or `~/.claude/CLAUDE.md`: those are your own files, not the repository's, and are always loaded.

Separately from trust, and **not** a security boundary, Settings → General → **Project docs** lets you switch individual instruction files off for one project — for example a `CLAUDE.md` a repository carries for a different tool. A switched-off file is skipped by name and by content, for that project's folder only: the selection does not inherit to child folders, a rule for one project does not affect another, and no rule means every file is loaded. Recording one never makes an untrusted folder inject anything, and it cannot grant access to skills, agents, hooks or MCP config — it only narrows the instruction files that folder trust already permitted. It is stored in `project_docs` in your `settings.json`.

**MCP servers start on launch.** Every enabled stdio MCP server is spawned as a subprocess when the app starts, with no confirmation. Their *tool calls* go through the permission gate, but by the time you are asked, the server's command has already run. Servers inherit your environment, so one configured with `GITHUB_TOKEN` in its env gets it. Only *your* configured servers are started — untrusted repositories cannot start servers by themselves. A trusted project may contribute project-local MCP configuration, and those declarations are surfaced in the trust review before you trust it.

**MCP OAuth is explicit account authorization, not tool approval.** Browser sign-in uses authorization-code PKCE and a temporary loopback callback listener. Access and refresh tokens remain backend-only in `mcp-oauth.json`, bound to the configured server name and resource URL. This file is plaintext, not encrypted credential storage; filesystem reads are not sandboxed. Disconnect removes local OAuth credentials and disables the server; revoke provider-side consent separately. A local Work IQ server handles its own Microsoft authentication and credential storage, so removing its OpenLeash configuration does not sign it out. Enabling any connector does not add tool approval rules.

**Hooks run shell, but only after you review them.** Settings → Checks & hooks lets you register a shell command that runs at a point in a run (before or after tool calls, when you send a message, when a run starts or ends, when a subagent or the run finishes). A hook is not a tool call, so it does not go through the permission gate: nothing asks you at the moment it runs. The control is instead **review by hash**. A hook does not run until you have approved the exact body that would run — its event, matcher, command and whether it may rewrite arguments — and the approval is recorded against a SHA-256 of that body in your own `settings.json`. Edit the command and the approval no longer matches, so the hook stops until you approve it again; Settings shows what changed. Project hooks are only read from a trusted folder and cannot approve themselves. Existing user hooks are grandfathered once, unchanged, so nothing you already relied on goes quiet. What remains outside the control: a hook you approve runs with your full user account and no sandbox, exactly as a shell command you ran yourself would, and a `pre_tool` hook you have given the "may rewrite arguments" power can change what a tool call does.

**A global keyboard hook is installed on Windows for the process lifetime.** `pcguard` installs a `WH_KEYBOARD_LL` low-level keyboard hook to catch `Esc` while another app has focus. A low-level hook cannot be uninstalled, so it stays active as long as OpenLeash runs. It inspects one key and is not a keylogger, but it will trip heuristic AV/EDR rules. The app is explicit about this in `src-tauri/src/agent/pcguard.rs`.

**Reply images and static diagrams.** Markdown HTTPS images load directly in the webview with lazy loading and `no-referrer`, including the full-size lightbox. This removes the referrer, not the request/IP address or all browser credential behavior; remote hosts may track access and URLs may expire. The app does not proxy/cache these images or guarantee that redirects/DNS resolve to public addresses. The existing main-window image CSP is unchanged. `openleash-svg` fences render through a data-URL image, never `innerHTML`, an object, or a script-enabled frame: SVG scripts and external subresources are disabled by image-context rendering. Malformed SVG can fail to display. Ordinary SVG fences stay source, and inline diagrams share the visualization byte/count bounds.

**Proof clips and visual diffs add no new capture path.** A proof clip (`browser {action: record_start}` / `computer {record: "start"}`) only keeps screenshots the agent's tools already take after their own checks: a viewport screenshot of the agent's headless browser after an action has run — so after a `click`/`type` approval, and never for one that was refused — or the picture a `computer`/`screenshot` call returned, which still needs the computer-use plugin on. A browser recording refuses desktop frames and one agent's recording never receives another's. A visual diff screenshots only http(s) URLs in the throwaway-profile browser; Review's **Recapture after** button launches a fresh one of those (not the agent's session) on your click, only while the browser plugin is on, and re-validates every stored URL first. Clips and screenshots are plain PNG files under `~/.openleash/proof/<chat>/`, outside the project so they are never committed, removed when the chat is deleted; like other local data they are not encrypted, and a clip of your screen shows whatever was on it.

**Inline artificts and visualizations are untrusted documents, not agent tools.** A successful `artifict_preview` tool call attaches a one-off artifict to the chat transcript; it is not a project artifict. Successful `artifict_create` and `artifict_revise` calls also attach an inline card, while writing the durable version under `.openleash/artificts/`. A plan-mode approval files the proposed plan in that same project store: that write is the harness recording the proposal it is already showing the user, not a tool the agent called, so it is not a permission prompt and not a way to write while plan mode is on — every model-initiated artifict write stays refused until the plan is approved. The card is a summary tied to the existing tool row; only after the tool succeeds and source passes size/type validation does its content render. HTML runs in the existing isolated visualization frame; SVG, Markdown, text, and JSON use inert renderers, and an `image` artifict only ever produces an `<img>` from an HTTPS, inline raster `data:` or project-relative file-path source — anything else is refused outright rather than fetched. The assistant may also use an exact, closed, top-level `openleash-viz` fence in a reply; that route auto-runs when complete, without a Preview click or user approval gate. Incomplete fences and running artifict-tool calls show a placeholder, not their partial source. These inline features remain ordinary chat data and never grant tools or permissions. Ordinary HTML/other code fences, raw HTML, user messages, approvals, and tool details are inert, with one exception: a bare, complete, top-level `<svg>…</svg>` block in an assistant reply is read as the same inert image-context diagram an `openleash-svg` fence produces — drawn as an `<img>` data URL, never inserted into the host DOM, with its scripts disabled. The host adds the app's text face and, for a source that asks for one, the app's own theme tokens as a same-document `<style>`: an image document has no host stylesheet, so without them a diagram drawn against the app's palette resolved to no colour at all. Styles are not scripts, and the document still cannot reach the network or the host page. The saved Artifict workspace still requires an explicit Preview click to run saved HTML documents. The app serves each generated HTML document from the independent `openleash-viz` custom-protocol origin, backed by bounded ephemeral memory, rather than `srcdoc` or a data URL (which inherit the parent CSP). The parent keeps `script-src 'self'` and allows only that visualization origin under `frame-src`. Every document response, including failures, denies network connections, external scripts/styles/images/fonts, frames, workers, forms, objects, and base URLs; inline generated scripts/styles and data images/fonts are allowed only inside the document. The one external script source is the same protocol's `/lib/` directory, where the host serves exactly one fixed file, `lib/echarts.js` (the bundled Apache ECharts build plus a theme shim, embedded in the binary at compile time); every other path there is a 404, and document ids are never under `/lib/`. Under remote access that file is served at `/__openleash/viz/lib/echarts.js` without a session — it is public library code, and a script request from the opaque-origin frame never carries the SameSite=Strict cookie — and a remote preview's policy names that server's own `/__openleash/viz/lib/` directory instead, only when the Host header is a plain host[:port]. `openleash-chart` specs are parsed by the host, re-serialized, and carried into the frame as an inert JSON script element with `<`, `>` and `&` escaped, so spec strings cannot become markup; the resulting chart runs with the same sandbox and the same lack of resource limits as any other visualization. The iframe and response CSP sandbox both grant only `allow-scripts`: no same-origin privilege, top navigation, popups, forms, or downloads. The persistent source lives in project files; the frame document itself is served from bounded process memory.

The optional preview-to-host protocol belongs to the visualization frame. It accepts only small allowlisted JSON messages from the exact currently displayed iframe and an opaque `null` origin; it validates shape, field lengths, size, nesting, rate, and count. A preview can propose a target/state only as untrusted draft data; it never invokes app commands, persists, submits, or reaches the agent until the user reviews it and explicitly presses **Send** in the artifict editor or on a saved artifict's inline card. That explicit send is the handoff: it records the request against the exact revision and delivers it to the agent as an ordinary chat turn, so pause, plan mode, hooks and permissions gate it exactly as they gate a typed message. Nothing a preview can do triggers a send, a save or a revision, and a request's quoted comments, points and state remain data the user entered rather than instructions or a permission grant. A preview can forge proposals, which are not proof of user intent. Inline artifict cards expose no privileged app/message bridge: the inline request box calls the same single submission command the editor does, which is the one path by which a request reaches the agent. Native webview messaging behavior remains platform-specific and must not be assumed absent.

**The studio's own writes are the user's, and the frame cannot make one.** Edit mode, source editing and **Restore** append a version through `artifict_edit` / `artifict_restore`, host commands the main window invokes on an explicit Save or Restore click. They take the project from the task record, not an argument, and are subject to the same parent-version check, size and revision limits as the agent's writes, so one that raced an agent revision is refused rather than overwriting it. Such a version is marked `author: "user"`; the agent's tool input has no way to set that field, so the agent cannot present its own revision as the user's. In Edit mode the frame only reports what was clicked (a bounded selector, label, the element's own text and a few computed styles); the pending edits live in the host, are sent into the frame only to be displayed, and are written by the host on Save. A text change is placed only where its original text occurs exactly once between two tags, and a style change only into one marked `<style data-openleash-edits>` block from an allowlisted set of properties with validated values, so nothing typed in the panel can close the element or inject markup. **Export** writes one stored version to a path the user picks in the native save dialog; the backend builds the file from the stored version and accepts only bounded, character-filtered theme values from the host. An exported HTML page is the same untrusted generated code, now outside the sandbox: opened in a browser it runs with that browser's normal network access and none of the preview's CSP.

There is no per-preview CPU, memory, or execution-time budget. Generated HTML can loop, consume CPU/memory, or hang the webview; Stop may not recover an already blocked renderer. One-off previews run without a separate Preview action, so never include secrets or sensitive data. The iframe restrictions do not sandbox resource usage or promise uniform behavior across native platforms.

Native webview implementations matter here. On Windows, WebView2 may inject Tauri bridge globals into subframes despite main-frame-only initialization flags; do not treat their absence as the boundary. A live probe on WebView2 149 confirmed sandboxed iframe native messages reached a separately subscribed frame observer, but not the top-level native handler; an `Origin: null` request to the app protocol is rejected. This is evidence for that tested Windows WebView2 version, not a cross-platform guarantee: Linux and macOS native messaging behavior has not been live-validated, and WRY's handler behavior may differ by platform. No app code subscribes to iframe native messages. Preserve the isolation controls when changing webview dependencies, and do not claim that app-level code absence proves native bridges are unreachable on every platform. Visualization execution is not a CPU/memory resource sandbox: generated code can loop or exhaust resources, and Stop may not rescue an already blocked renderer. Do not enter secrets into a model-generated UI.

## App updates

The in-app updater is separate from the agent's tools.

**App updates are separate from agent tools.** The app checks the public
`DevLeashed/OpenLeash` GitHub latest release on startup and periodically; these
requests disclose the usual network metadata/IP address to GitHub, not task
transcripts or provider credentials. Install-capable builds download newer stable
updates in the background. **Released update packages are not signed and the app
does not verify an update signature**: the only protection on that path is TLS
plus the pinned `DevLeashed/OpenLeash` release path that `src-tauri/src/updates.rs`
enforces before any bytes are fetched, so whatever can serve the update manifest
also decides what the app will run. Re-enable minisign verification before
treating in-app updates as authenticated. Applying an update and restarting
requires an explicit user action and is refused while agent/background work is
active. Portable Windows, macOS and non-AppImage Linux builds announce releases
instead of installing them. See [Releases](releasing.md) for setup and supported
packages. Unsigned updates are also not Windows Authenticode signing or macOS
signing/notarization, and neither removes SmartScreen or Gatekeeper warnings.

**The GitHub connector's token only goes to GitHub.** A raw `api` call to a path that is not on `api.github.com` is treated as a write, so it asks — otherwise a prompt-injected repository could post your token to any host without a prompt.

**Language servers are programs the project configures.** The `lsp` tool asks a language server (rust-analyzer, typescript-language-server, pyright/basedpyright/pylsp, gopls, clangd) about the code. The questions are reads, but starting a server is not: rust-analyzer runs `cargo metadata`, which honours a repository's `.cargo/config.toml` and `rust-toolchain.toml`; gopls follows `go.mod`'s toolchain line; pyright may start a project venv's interpreter. So `lsp` is **not** a read-only tool. It runs without asking only on Full access, and asks on every other rung, offering an "always" rule per server and project (`lsp:rust-analyzer`). Plan mode asks even on Full access, so a server never starts unseen while you are reviewing a plan; an explicit allow rule still applies there. Deny rules (`!lsp`, `!lsp:gopls`) win as always. The command line is fixed by the app, never by the model, a setting or the repository. The executable is looked up on your `PATH` skipping any entry inside the project and any relative entry, so a repository cannot plant its own `rust-analyzer`. Servers start in their own folder rather than the project's, so npm `.cmd` shims cannot pick up a project-local `node`. rust-analyzer is started with build scripts, proc-macros and check-on-save turned off. Servers never apply edits (`workspace/applyEdit` is refused) and are never told to save. Environment files are not opened. These limit what a hostile repository gets, but they do not make a language server safe on an untrusted project: only allow it on projects you trust. Servers are shared across chats, shut down after 15 idle minutes, and stopped when the app exits. They are not available for SSH or WSL projects yet.

**`wait_for_event` only watches.** A parked chat can wake on a timer, on GitHub CI or a PR (through the GitHub plugin), on a file or folder changing (`stat` only: a folder is walked honouring `.gitignore`, and nothing is read or run), on one of *that chat's own* background commands exiting or printing a regex match, or on another chat stopping work (only while **Other chats** is on: it reads the same status `list_chats` shows). None of these runs a command, fetches a URL or writes anything, which is why parking is not a permission prompt. The follow-up turn the wake starts is an ordinary turn under the chat's own permissions. A park does not survive an app restart.

**The Linear, Jira, Slack, Notion and GitLab plugins act as you.** Their tools use your token, so anything they change — an issue, a transition, a Slack message, a Notion page, a merge request, a pipeline retry — is done under your name. Reads run without asking (a prompt-injected page or issue can therefore steer the agent into *reading* whatever your token can read); every write asks unless you allowed that action (`<plugin>:<action>`), allowed the whole plugin (`<plugin> *`) or use Full access. Plan mode refuses writes and read-only subagents cannot make them. Classification fails closed: an unknown action is a write, a raw `api` call is a read only for a GET to a relative path, and a Linear `graphql` document is a read only when it contains no mutation or subscription and parses cleanly. Raw `api` paths for Jira and GitLab are pinned to the configured host — protocol-relative (`//host`), absolute URLs on another origin, `user@host` tricks, backslashes, encoded leading slashes and control characters are refused before a request is made, so the token is never sent elsewhere. The tokens are stored in plaintext in `settings.json` like other keys (environment variables are an alternative); they are never returned to the settings UI, never written into a chat's saved plugin snapshot, and are redacted from error messages.

## HTTP requests

**`http_request` can write to anything it can reach, so the gate depends on the method and the target.** Unlike `web_fetch`, the tool takes any method, headers and body, and may reach this machine and the private network when you approve it. Before the permission check, every URL is put into one of four classes:

- **Public:** anything not listed below.
- **Loopback:** `localhost`, `*.localhost`, `127.0.0.0/8`, `::1`, `0.0.0.0/8` and `::`.
- **Private:** RFC 1918 ranges, CGNAT `100.64.0.0/10`, unique-local `fc00::/7`, undotted intranet names, and `.local`, `.internal`, `.lan` and `.home.arpa` names.
- **Blocked:** link-local `169.254.0.0/16` (including the metadata endpoints `169.254.169.254` and ECS `169.254.170.2`), `fe80::/10`, AWS IPv6 metadata `fd00:ec2::254`, Alibaba `100.100.100.200`, Oracle `192.0.0.192`, multicast, broadcast, reserved `240.0.0.0/4`, and metadata names such as `metadata.google.internal`, `metadata.goog` and `instance-data`.

IPv4 written in decimal, hex, octal or short form is normalized by the WHATWG URL parser before it is classified, and IPv4 embedded in IPv6 (`::ffff:a.b.c.d`, `::a.b.c.d`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) is classified as that IPv4 address. The check in `src-tauri/src/agent/permissions.rs` then applies, deny tier first:

| Request | Disabled | Allowlist / Reviewer | Auto | Full Access | Plan mode |
| --- | --- | --- | --- | --- | --- |
| `GET`/`HEAD`, public | allow | allow | allow | allow | allow |
| Other method, public | deny | ask | ask | allow | deny |
| Any method, loopback or private | deny | ask | ask | ask, never silent | `GET`/`HEAD` ask, others deny |
| Any method, blocked target | deny | deny | deny | deny | deny |
| Invalid method, invalid URL, or userinfo in the URL | deny | deny | deny | deny | deny |

**Allow rules are exact.** **Always allow** on the card records `http_request:<METHOD> <scheme>://<host>:<effective-port>`, for example `http_request:POST https://api.example.com:443` or `http_request:POST http://localhost:3000`. The effective port is always written, including the default, and scheme is part of the key: a grant for `https://localhost:443` cannot authorize `http://localhost:80`. It matches that method, scheme, host and port only: never a subdomain, another host or another method, and no wildcard allow rule is honoured. Deny rules remain method-and-host patterns: `!http_request` or `!http_request *` refuses the whole tool, and `!http_request:POST api.example.com`, `!http_request:* api.example.com` or `!http_request:DELETE *` refuse matching calls, case-insensitively. Denies are re-applied to the effective method and authority at every redirect hop, so a hop to a host denied by `!http_request:* b.example.com` is refused. A deny always wins, over Full Access and over a `GET` that would otherwise run without asking.

**Every call takes the ordinary gate.** Plan mode, the deny tier, doom-loop protection and reviewer mode apply to it like any other tool. Read-only subagents are offered only `GET` and `HEAD`, and any other method is refused at dispatch as well, so a schema the model ignores does not widen it. Other subagents get every method through the same gate. The tool is not exposed over MCP. In an SSH project the request leaves from the computer running OpenLeash, so `localhost` and the private network are yours, not the SSH host's.

**The address is checked again when the request is made.** The hostname is resolved before connecting and every resolved address is classified. A blocked address is always refused, and a URL that looked public but resolves to a loopback or private address is refused, which closes the DNS-rebinding and internal-DNS gap `web_fetch` still has. The connection is pinned to the addresses that were checked, so a second DNS answer cannot move it. System proxy settings are ignored, because a proxy would resolve the name itself and defeat the check; the tool therefore does not work on networks that only allow traffic through a proxy.

**Redirects are followed by hand, one checked hop at a time.** Each hop is re-validated and re-resolved. A redirect to a blocked target is refused. A redirect to a loopback or private target is refused unless it stays on the approved request's origin (scheme, host and port). A `307` or `308` that would resend a non-`GET` method and body to a different origin is not followed: the 3xx response is returned, and the agent has to make a new request that is approved on its own. A `301`, `302` or `303` after a non-`GET` becomes a `GET` without a body. `Authorization`, `Cookie` and API-key-like headers are dropped on any cross-origin hop.

**Secrets are redacted where you look at the call.** The approval card, the stored input of the transcript row (which is also what ACP clients see), the doom-loop card and the reviewer model's prompt all show redacted values. `Authorization` and `Proxy-Authorization` keep only their scheme (`Bearer [redacted]`). `Cookie`, `Set-Cookie` and any header whose name contains `token`, `secret`, `key`, `auth`, `password`, `session`, `signature`, `credential` or `cookie` become `[redacted]`, and so do query parameters with such names (and `code` and `sig`). JSON body keys with such names are redacted recursively, and form-encoded bodies the same way. A URL path segment or query value that looks like a random token (24+ letters and digits, e.g. the secret part of a Slack or Discord webhook URL) is redacted too; UUIDs are left alone.

**What this does not protect against:**

- Redaction is for display only. The model already saw any secret it put in a header, and the raw tool input is stored in the task's conversation history on disk and sent to the model provider.
- A secret written as free text inside a body that is neither JSON nor form-encoded is not detected.
- Trusted `pre_tool` and `post_tool` hooks receive the raw input.
- A `GET` to a public host runs without asking, as `web_fetch` does, so it can carry data out in the URL or headers to any public host just as `web_fetch` can. Deny rules are the control for that.
- An approved loopback request can still change local state, such as a dev server's database.
- Response bodies are untrusted data, the same as a fetched page.
- TLS errors cannot be bypassed: there is no insecure option.
- None of this is a sandbox.

## Other chats

**An agent can read and message your other chats — on by default; turn it off to stop it.** With Settings → Chats → **Other chats** enabled (the default), a chat's main agent gets `list_chats` (search your chats and see what each is doing) and `message_chat` (send one of them a message). Both are on by default, and the setting is the switch. This is the one capability that reaches *outside* the conversation you opened: an agent can read the state of chats it was never given, and a message it sends starts or continues work in one of them. Subagents never get either tool; only a chat's main agent does. `message_chat` goes through the permission gate like any other action, so under Full Access it runs without asking and everywhere else it asks unless you always-allow `message_chat *`. Plan mode refuses it, and a deny rule on either name wins over everything, as deny rules do.

**What a message can and cannot do.** It is delivered to the other chat as a note from another agent — never as your own words. It does not append a user turn to that chat's history, does not draw a user bubble in its transcript, does not run that chat's `user_prompt_submit` hooks, and cannot approve, answer or unpause anything there. A chat that is paused refuses, and a chat held by *Pause all* refuses too: **a frozen chat cannot be thawed this way.** An archived chat refuses as well. `list_chats` is a read of task metadata only — title, status, current step, project, branch and activity time — and never returns a transcript, a file, a credential or another chat's tool results.

**It is not an isolation boundary.** The receiving chat still does only what it is allowed to do, under its own permission rung, plan mode and deny rules, unchanged. So a message is not a grant of authority, and it cannot be used to escape a restriction placed on the chat you are in — but an agent already permitted to edit files can be asked by another agent to edit them, which is a real consequence of turning this on. That is why it is off until you ask for it. Turning the switch off refuses both tools for new chats immediately, and a chat already running is told the rules changed; anything you already sent stands.

## Discord connector

**An allowed Discord user can drive the agent.** The bot creates and continues real chats on this machine. Anyone whose Discord user id is on the list can make the agent edit files and run commands in the configured project, up to the permission mode chosen for Discord chats, and can answer that chat's approvals by replying. The security of the connector is therefore the security of those Discord accounts: use two-factor authentication on them, and prefer Auto-edit or Allowlist over Full Access. Full Access means a message runs anything without a check.

**The gate is the user-id list, and it fails closed.** A message reaches the agent only if its author's id is listed (`connectors/discord.rs`, `gate`). With an empty list the bot doesn't connect, and nothing is let in. Server, channel and DM settings only narrow access further. They are checked after identity, so a stranger is refused wherever they post. Messages from bots, including this one, are always ignored. The bot never pings anyone: posts are sent with `allowed_mentions` empty.

**The token is stored like other local credentials, not encrypted.** The bot token lives in `~/.openleash/connectors.json`, kept out of `settings.json` so that the generic settings patch, the settings sent to the UI and shared configs never carry it. It is set through a write-only command and never returned over IPC. The UI only learns whether one is set. The file is owner-only on Unix and inherits the profile ACL on Windows. Anything running as your user can read it. The channel → chat links are in `discord-chats.json`.

**Discord sees the conversation.** Your messages, the agent's replies, approval prompts (including the command or file path being approved) and question text pass through Discord's servers. Don't use the connector for work you wouldn't post in a Discord DM.

**Messages are framed as chat input, not instructions from the harness.** The bridge appends a reminder that the message came from Discord, with the author's id and where it was sent. Display names are stripped of `<`, `>`, backticks and control characters before they are embedded, so a username can't close or forge that reminder. An approval reply is approved only when it is clearly a yes (`yes`, `ok`, `👍`, and similar short replies, or `always`). Any other text denies it.

Replies are sent as plain text (no Markdown or HTML parse mode). An approval reply is approved only when it is clearly a yes (`yes`, `ok`, `👍`, and similar short replies, or `always`). Any other text denies it.

## Slack connector

**An allowed Slack member can drive the agent.** The app creates and continues real chats on this machine. Anyone whose Slack member id is on the list can make the agent edit files and run commands in the configured project, up to the permission mode chosen for Slack chats, and can answer that chat's approvals by replying. The connector is therefore only as secure as those Slack accounts and your workspace's sign-in policy. Use two-factor authentication or SSO on those accounts, and prefer Auto-edit or Allowlist over Full Access. Under Full Access, a message runs anything without a check.

**The gate is the member-id list, and it fails closed.** A message reaches the agent only if its author's id is listed (`connectors/slack.rs`, `gate`). With an empty list the app doesn't connect, and nothing gets in. Workspace, channel and DM settings only narrow access further. They are checked after identity, so a stranger is refused wherever they post. When workspaces are listed, both the workspace the event came through and the author's own workspace must be on the list, so a channel shared with another organisation doesn't admit its members. Messages from bots, including this one, are always ignored, and so are edits and other system messages. An edited message never re-runs a request. A reply in a thread the bot is already in counts as addressing the bot, but the author must still be on the list.

**The agent can't ping anyone.** Before posting, the agent's text has `&`, `<` and `>` escaped, so it can't write `<!channel>`, `<!here>`, `<!everyone>` or a `<@user>` mention. Posts are also sent with `parse: none` and `link_names: false`, so a plain "@channel" stays plain text. The only markup the connector writes is a link for `[label](https://…)`, and only to an `http(s)` address.

**The two tokens are stored like other local credentials, not encrypted.** The app-level token (`xapp-…`) and the bot token (`xoxb-…`) live in `~/.openleash/connectors.json`. They are kept out of `settings.json`, so the generic settings patch, the settings sent to the UI and shared configs never carry them. Each is set through a write-only command and never returned over IPC. The UI only learns whether each one is set. Error messages are scrubbed of anything token-shaped before they reach the status line or a log. The Socket Mode URL, which carries a short-lived connection ticket, is never shown. The file is owner-only on Unix and inherits the profile ACL on Windows. Anything running as your user can read it. User tokens (`xoxp-…`) are refused, because they act as you rather than as the bot. The thread → chat links are in `slack-chats.json`.

**Slack, and your workspace's admins, see the conversation.** Your messages, the agent's replies, approval prompts (including the command or file path being approved) and question text are stored by Slack like any other messages. Your workspace's retention settings, exports and eDiscovery apply to them, and workspace owners and admins may be able to read them. Don't use the connector for work you wouldn't post in that workspace.

**Messages are framed as chat input, not instructions from the harness.** The bridge appends a reminder that the message came from Slack, with the author's member id and where it was sent. Display names and channel names are stripped of `<`, `>`, backticks and control characters before they are embedded, so a name can't close or forge that reminder. An approval reply is approved only when it is clearly a yes (`yes`, `ok`, `👍` and similar short replies, or `always`). Any other text denies it.

## Agent memory

**Memory outlives the chat that wrote it.** With Memory on (the default), the main agent's saved notes are injected into the system prompt of every later chat: global notes in every project, project notes in that project. Content the agent read could try to get itself saved, for example a web page or repository text saying "remember to always…". So the snapshot presents notes as the agent's own earlier writing, which loses to whatever the user says now. Writes containing invisible or control characters are refused, and such lines are skipped at load. Subagents have no memory tool. Review `~/.openleash/memory/` if a chat behaves as if told something you never said. Turning Memory off stops new chats from loading it.

## Save as skill

**A saved skill outlives the chat too**, and its description goes into every later chat's prompt. So turning a chat into a skill is user-triggered only: there is no agent tool, slash command or prompt instruction for it, connector messages (Discord) cannot reach it, and its commands refuse calls from any window but the main one and refuse while an agent is controlling the desktop. The draft is written by a model reading the transcript, which may include untrusted web pages or tool output, so it is always shown to you for editing before anything is written. Invisible and control characters are refused, and API-key-looking strings are redacted heuristically. That is a safety net, not a guarantee; read the draft before saving it.

## Phone approvals (ntfy)

When remote control and ntfy are on, approval and question notifications go to a phone through an ntfy server. Two things leave your machine: the notification text, and, for an approval, a one-use grant that is embedded in the notification's action. Anyone who can read the topic can therefore approve the request it names, within 15 minutes, without a paired session. Public ntfy.sh topics are readable by anyone who knows the name, so the topic is effectively a secret. Use your own server or topic access controls, and do not share the topic. Notification text is withheld unless **Show chat name and command summary** is on for that device. Access tokens are write-only in the UI and stored in `remote.json` beside the other remote secrets. See [Remote control](remote.md#phone-approvals-with-ntfy).

## Headless and editor entry points

`openleash-headless` and `openleash-acp` run the same agent loop and permission gate as the desktop app; they add no bypass. The headless CLI has no one to answer an approval, so it exits with code 4 when a prompt would block, rather than approving it, and its default mode is `allowlist`. The ACP server forwards each approval to the editor as `session/request_permission`, and runs its sessions in `allowlist` mode. Neither entry point changes deny rules, plan mode or the protections described above. Their stdout and the editor session carry model output, which is untrusted data.

## Remote control

**A paired device is you.** Remote control has full parity with the desktop window: a paired browser can approve tool calls, switch to Full Access, edit hooks, change settings and read files through the app. Treat a pairing link, QR code or six-digit code like a password while it is on screen, and revoke devices you no longer use (Settings → Remote).

**Every request needs a session, wherever the server listens.** The server is off by default and binds loopback unless you choose *Network*. Even on loopback, every page, asset and WebSocket requires a session cookie. A tokenless localhost server can be driven by any website you visit, through DNS rebinding or a cross-site request, so OpenLeash doesn't run one. Sessions are `HttpOnly`, `SameSite=Strict` cookies, and only their SHA-256 is stored in `~/.openleash/remote.json`. WebSocket upgrades must also carry an `Origin` naming the exact host they reached. Pairing secrets are compared in constant time. Six-digit codes expire after five minutes, are single-use, and burn after five wrong guesses, and an address with ten failures is locked out for ten minutes. Pages carry a strict CSP and `frame-ancestors 'none'`.

**Remote calls take the main window's path.** Invokes from a paired browser go through the main webview's own Tauri IPC entry point, so they are subject to the same capability (`capabilities/default.json`) as a click in the window. The PC-control guard webview and its narrower capability are never used. Desktop-window events (`tauri://…`, such as drag-and-drop) are not forwarded to remote pages.

**Network mode is plain HTTP.** On a LAN, traffic and session cookies can be read by anyone who can watch the network. Prefer loopback plus an SSH tunnel, or a private overlay such as Tailscale.

**SSH connections use your SSH client and trust.** *Other machines over SSH* runs the system `ssh` with `BatchMode=yes`, reads the other machine's pairing secret over that SSH session (anyone who can log in as you there can already read it), and forwards a local port. OpenLeash never sees SSH keys or passwords and never accepts host keys for you. Destinations that look like options (`-o…`) or contain shell syntax are refused.

**A transferred chat is untrusted data.** *Send to another machine* copies a chat file into the receiving machine's `~/.openleash/imports/`, and the import treats it like any file from elsewhere. It reads only a plain `.json` name inside that folder (no separators, no `..`), refuses files over 1 GiB, and rebuilds or drops everything in a task file the app would act on: the frozen system prompt and tool list, plugin config, read-before-write timestamps (a forged one would skip the read check), revert contents (a forged one would write arbitrary text to an arbitrary path), checkpoints, stop notes, background-command and docker state, and worktree paths. The permission level is capped at the receiving machine's default; plan mode is kept. Trust, allow rules and approvals are never in a bundle: the folder the chat lands in is trusted or not by the receiving machine's own decisions. Strings from the sending machine are stripped of `<`, `>`, control characters and newlines, and length-capped before they appear in the move notice the agents read. The import command can be called by any paired device, consistent with "a paired device is you".

## Remote-SSH projects

**A remote project's host is a second computer the agent acts on.** In a project opened over SSH (`ssh://<host-id>/<path>`), the agent's file tools, commands and git run on that host as your SSH user, with the same permission ladder, deny rules, plan mode and subagent restrictions as a local project. The permission layer is not a sandbox there either: reads are unconfined, and a command you approve can do anything your account on that host can.

**Containment is decided on the remote realpath.** A write's target and the project root are both resolved by the server (`realpath`, plus a component walk for paths that don't exist yet, following dangling symlinks to where the write would land), compared case-sensitively and on the same host, and the write then goes to exactly the resolved path. A remote `proj/link -> /etc` therefore counts as outside the project; a lexical comparison of `ssh://` strings is never used as a containment proof. Read-before-write keeps a content hash next to the mtime, because SFTP mtimes are whole seconds.

**`ssh://` strings never reach local file or process APIs.** On Windows `ssh://h/x` would be a relative local path, so the local file tools, the local shell, hooks' working directory, checkpoints, worktrees, docker and artificts refuse such a path (the last four with "not yet supported for SSH projects") instead of guessing.

**Trust is per host and per path.** A trust decision for `ssh://A/home/me/app` covers neither the same path on host B, nor the local folder `/home/me/app`, nor `ssh://A/home/me/App`. A trusted remote project contributes its instruction files only; its skills, agents, hooks and MCP servers are not loaded. Your own hooks still run, on this computer.

**What `ssh` connects to is not the agent's choice.** A project names a saved host by id, the target is looked up in your settings at connection time, and the agent's paths may only name the project's own host. OpenLeash uses your `ssh` client with `BatchMode=yes` and never handles keys, passwords or host-key decisions. Remote commands are quoted as single shell words (cwd, command and environment), and machine-read output (git, file lists, probes) is taken only after a marker line, so a login profile that prints text can't be mistaken for data.

## Docker workspaces and WSL

**A container is isolation for the project, not a sandbox for the agent.** In a docker workspace the agent's shell commands run inside the container, but its file tools still run on the host (confined to the workspace by the usual write checks, while reads remain unsandboxed as described above). The container also has whatever the Docker daemon grants it. OpenLeash never passes `--privileged`, extra capabilities, the Docker socket, host networking or host mounts other than the workspace. `openleash.json` cannot add them, published ports bind `127.0.0.1` only, and copying a non-git project skips symlinks so the container cannot write through one to the host. Building the image runs the project's own `RUN` steps, so docker mode is only offered for trusted folders.

**Containers are labelled and owned by the harness.** Only containers labelled `openleash.task` are listed or removed by the workspace manager, and one that belongs to an existing chat cannot be pruned from there.

**WSL projects run commands inside the distro.** A project at a `\wsl.localhost\<distro>\…` path has its shell commands, hooks and git run through `wsl.exe --exec` in that distro, with the same permission checks as local commands. The command string reaches bash as one argument, with no intermediate shell parsing it. A Linux path under `/` is mapped to the UNC path of the same distro, and paths containing `..` are not mapped.
