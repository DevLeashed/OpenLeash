# Features

Everything OpenLeash does, and why. Back to the [README](../README.md).

These are the ideas taken from Claude Code and ZCode, and why each one matters:

## Collaborative project artifacts (optional)

Each chat has an optional **Artifacts** view backed by the current task's project folder at `.openleash/artifacts/`; artifacts are shared between chats for that project. Agents can create purposeful HTML/SVG/Markdown/JSON deliverables, record decisions, constraints and relative code references, and append immutable revisions. You can compare specific versions and ask the agent to revise their content or metadata. For revisions, the agent must name the current parent version; stale writes fail rather than silently replacing newer work.

The default remains ordinary chat: users can send a message and let the agent work without opening this workspace. Annotations and preview proposals are editable host-side drafts tied to one version. The workspace puts a simple **What would you like to change?** field directly below the preview. **Advanced feedback** holds optional annotations and interactive state; you can inspect what will be included and explicitly **Send feedback to agent**. Only this action makes the request and selected notes/state visible to artifact tools. Drafts are kept separately for each exact version while the workspace is open, survive failed saves/sends, and are restored when switching back to that version. Closing the workspace discards unsent local drafts. Drafts are not inserted into the transcript or system prompt. The agent can respond, acknowledge they need clarification, and create a new revision; the prior version stays available for comparison. See the [collaboration smoke-test prompt](collaboration-smoke-test-prompt.md).

Project artifacts are human-readable, repository-controlled data—not trusted instructions or secure/private storage. Reads and shell access are not sandboxed, so an agent can still inspect the checkout directly; never put secrets in artifacts. Generated HTML is untrusted code and preview remains subject to the limits in [Security](security-model.md).

## Inline artifact cards

When a visual or structured deliverable materially improves an answer, the agent can choose a temporary `artifact_preview` or a durable `artifact_create` / `artifact_revise`—without asking you to choose a mode. Ordinary chat remains the default; artifacts are optional, not a goal to satisfy on every turn. A card appears at its tool call's position in the transcript, before the assistant's final reply. While the tool runs, it shows **Building…**; partial tool JSON and source stay hidden. A preview is attached only after its complete input validates and the tool succeeds.

A **one-off** preview is stored with that chat's transcript, so it appears again when you reopen the same chat. It is never written to `.openleash/artifacts/` and is not shared as a project artifact. `artifact_preview` supports HTML, SVG, Markdown, and JSON, with a 240 KiB source limit. A **saved** artifact is stored under the project's `.openleash/artifacts/`, remains available across chats, and is also shown inline. Its card distinguishes saved from one-off and offers **Open in Artifacts** for that exact saved version.

On success, inline HTML starts automatically in the existing isolated preview; its **Source** control lets you inspect the completed HTML if you choose. **Expand preview** opens a large host-controlled viewer without restarting the document or losing its live state; **Collapse preview** returns it to the card. Escape closes the viewer when focus is in the host controls (not inside the isolated document). The workspace artifact list can also be hidden to give previews more room. SVG, Markdown, and JSON are displayed inertly rather than run as active documents. This is separate from an `openleash-viz` fence in an assistant reply; both are inline chat experiences, but a tool-backed artifact card is produced by a successful artifact tool call. In the Artifacts workspace itself, saved HTML still requires an explicit Preview click.

[T3 Code's HTML-render guide](https://github.com/pingdotgg/t3code/blob/main/docs/user/html-renders.md) is a conceptual UX reference for visual replies inside a thread. The guide describes cross-provider inline visual replies separately from MCP Apps—tool-returned iframe UI the current guide says is supported by Codex. [Merged PR #15968](https://github.com/pingdotgg/t3code/pull/15968) describes T3 Code's attachment-based `html_render`. These are inspiration, not a claim of implementation parity: OpenLeash uses its own artifact tools, chat transcript persistence, and isolated preview. See [Security](security-model.md) for its limits.

## Needs you inbox and quick navigation

The optional **Needs you** sidebar inbox collects chats blocked on a question or approval so you can jump directly to the pending card. It never answers a question or approves an action on your behalf. The sidebar footer bookmark shortcut has been replaced by a direct **Accounts** shortcut to Settings → Accounts; saved prompts remain in the sidebar list and new-chat flow.

## Human steering and waiting on the agent

Projects can stay in the ordinary chat workflow. Task todos/status, per-chat pause/resume, message-while-running steering, and optional `ask_nonblocking` questions all help you intervene without needing a dashboard or artifact. Use the inbox only when a blocking question/approval is waiting for you.

For information that needs no answer, the agent can use `notify_user` with a title, message, and optional `info` or `warning` level. The agent continues immediately. A readable notice stays above the chat composer until you explicitly dismiss it; notices from other chats remain visible in the app's notification area. Pending notices survive app restarts, and dismissal is saved without sending an answer or resuming a run. Desktop notifications follow the existing notification setting and OS permission, fire while the app is in the background, and use generic copy rather than exposing the notice message outside the app. Archived or hidden chats do not display notices. Dismissed notices remain as receipts in the transcript.

## Interactive inline visualizations

Assistant replies can include a self-contained HTML/CSS/JavaScript block in an exact, closed, top-level `openleash-viz` fence. Once the fence is complete, it renders inline and runs automatically—there is no Preview step. While that block is still streaming, the card shows a friendly **Working on the interactive preview…** placeholder rather than exposing the unfinished source. **Source** is the control for users who choose to inspect the code. The assistant can still include normal inline text and ordinary code fences before or after a visualization; only exact, closed `openleash-viz` fences in assistant replies execute. Ordinary HTML/other fences, raw HTML, user messages, approvals, and tool details remain inert. Saved HTML documents in the separate project Artifacts workspace still need an explicit Preview click. These chat visualizations are full local JavaScript interactions (charts, calculators, diagrams, and demos), not a constrained chart language; external libraries and resources cannot be loaded.

Keep visualizations purposeful, self-contained, accessible, and responsive. An inline chat visualization offers **Source**, **Copy source**, **Expand preview**, and **Stop** controls. Expansion preserves the current iframe and its interactive state; it does not publish another document. If automatic publication fails because the bounded renderer registry is full, Source remains available and Retry preview can try again. Theme tokens are `--bg`, `--fg`, `--card`, `--muted`, `--accent`, `--primary`, `--border`, `--chart1`–`--chart6`, `--font-sans`, `--font-mono`, and `--radius`. Reopening a transcript can render a visualization again; it does not restore the prior live runtime. Up to eight visualizations per reply qualify, each with at most 240 KiB of source; empty, oversized, excess, or unfinished exact-tagged blocks show a non-code placeholder with an optional Source disclosure. Published documents live only in bounded process memory (64 documents / 8 MiB total, 30-minute expiry), not files.

Automatic JavaScript execution in chat increases exposure: model-generated code starts running as soon as its exact fence is complete. The iframe uses a separate visualization origin and strict sandbox/CSP controls; it has no network, filesystem, native IPC, or app/message bridge. These controls reduce capabilities but do not make generated code trustworthy or resource-safe. There is no per-visualization CPU, memory, or execution-time budget: a loop or allocation can consume CPU/memory or hang the webview, and Stop may not recover an already blocked renderer. Do not include secrets or sensitive data in a visualization or enter them into its UI. See [Security](security-model.md) for implementation details and platform-specific caveats; native webview behavior is not guaranteed uniformly across platforms.
