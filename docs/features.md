# Features

Everything OpenLeash does, and why. Back to the [README](../README.md).

These are the ideas taken from Claude Code and ZCode, and why each one matters:

## Remote connectivity

Remote control serves the full app to paired browsers: phones pair by QR code or a six-digit code, with per-device sessions, revocation, and a titlebar indicator while anyone is connected. *Other machines over SSH* tunnels to another computer's OpenLeash and opens it already paired. Projects at `\\wsl.localhost\…` paths run their commands and git inside the distro. Details: [remote.md](remote.md).

## Opening a project

The project menu (the folder chip on the home screen and the titlebar project selector) offers these ways in: **Open folder…** (`Ctrl O`), **Open from WSL…** (Windows, when a distro is installed: pick the distro, then a folder inside it, see [WSL projects](remote.md#wsl-projects)), **Clone repository…**, and **Open over SSH…** (a folder on another machine, where the agent's tools then run, see [Open over SSH](remote.md#open-over-ssh)). Clone takes a GitHub link (web links such as `…/tree/main/src` are cut back to the repository), any `https://` / `ssh://` URL, or `git@host:owner/repo`, shows where it will go, and clones into `~/openleash/<repo>` (`%USERPROFILE%\openleash` on Windows; not the hidden data folder `~/.openleash`). A name already taken becomes `<repo>-2`, `-3`, …; a folder that is already a checkout of the same repository is opened instead of cloned again. It uses your own `git` and its credentials (no terminal prompts), refuses option-like, local-path, `file:` and `ext::` inputs before git ever runs, and removes the folder again if the clone fails. The cloned folder is then opened like any other, so folder trust is asked about as usual. Code: `agent/projects.rs`, `ui/OpenProject.tsx`.

## Workspaces: local, worktree, docker

A task works in the project folder, in a git worktree, or in a docker workspace: a private clone or copy of the project with commands run in a container built from `.openleash_docker/`. The harness builds the image (and rebuilds it whenever that folder changes), starts the container when you message the chat, stops it when idle, and removes it with the chat. Settings → Workspaces manages every worktree and container, including leftovers. Details: [workspaces.md](workspaces.md).

## Best-of-N race

Turn on **Race** in the new-task composer (or type `/race`) to send one prompt to 2–6 independent attempts, each its own chat in its own git worktree, with its own model and effort (defaulting to the current model repeated). The attempts are grouped in the sidebar and each runs with the chat's permission mode, the monthly budget gate and usage caps exactly like a chat you started by hand. When every attempt has finished, or when you click **Judge now**, the project's automatic checks (the same `tsc` / `cargo check` / `go build` / Python checks the in-chat diagnostics run, and only while Diagnostics is on) run on each worktree, then a judge model (default: the first attempt's model, changeable per race) ranks the attempts with reasons. The judge is a single tool-less request that sees only the diffs and check output, so it cannot read, write or run anything, and an automatic judge never crosses the budget cap without asking. The comparison view shows every attempt side by side — status, diff stats, checks, cost and time, rank and reasoning — with **Open chat** and **Pick winner**. Picking a winner never merges by itself: **Merge winner** asks first, commits any uncommitted work in the winning worktree, and `git merge --no-ff`s its branch into the project's current branch (refused when the project has uncommitted changes; a conflicting merge is aborted and leaves the branch as it was). **Clean up losers** deletes the other attempts' chats with the same worktree warning as deleting any chat. Each attempt card also has **Stats** (tokens in and out, cache reads and writes, cache hit rate, context used, cost, cost per changed line, time and the model's price) and **Open folder** (opens that attempt's worktree in the file manager). The sidebar group shows how many attempts have finished while the race runs, and the comparison view shows the race's total cost. **Archive race** puts the race away together with its attempt chats, with an Undo; Settings → Chats lists archived races with **Restore**, which brings back only the chats archiving moved, so a chat you archived yourself stays archived. "Delete archived chats" also drops an archived race once all its chats are gone. Races are recorded in `~/.openleash/races.json`; a judge interrupted by quitting the app is marked failed and can be re-run. Code: `src-tauri/src/agent/race.rs`.

## Application updates

Desktop builds check the latest stable GitHub release and automatically download unsigned updates where package support permits. Updates never interrupt active agent/background work: restart and install are explicit user actions. Windows NSIS installs and Linux AppImages support in-app installation; released packages are not signature-verified, so see the [security model](security-model.md#app-updates). macOS DMG downloads, portable Windows executables and Linux Debian packages show a release announcement/link instead. See [release setup](releasing.md) for the signing-secret and asset workflow; updater signatures do not provide Authenticode signing or macOS notarization.

Each chat has an optional **Artificts** view backed by the current task's project folder at `.openleash/artificts/`; artificts are shared between chats for that project. Agents can create purposeful HTML/SVG/Markdown/JSON/text/image deliverables, record decisions, constraints and relative code references, and append immutable revisions. You can compare specific versions and ask the agent to revise their content or metadata. For revisions, the agent must name the current parent version; stale writes fail rather than silently replacing newer work.

You can also change an artifict yourself, the way a design tool lets you. **Edit** mode (`E`) on an HTML design lets you click an element and change its text, colours, font size, weight, padding and corner radius live, then save the result as a new revision; **Edit source** does the same for the source of any kind; and **Restore** puts an older version back as a new revision. These versions are marked as yours, and the agent is told to build on them rather than revert them. **Export** saves the version on screen through the system save dialog — an HTML design as a standalone page, SVG/Markdown/text/JSON as themselves, an embedded picture as its image file. A project's design system lives in `.openleash/DESIGN.md`, read like the other instruction files (trusted folders only, switchable in Settings), and the agent builds visual artificts from it; **Ask the agent → Set up a design system** asks for one. See [Artifict collaboration](artifict-collaboration.md) for the details and limits.

A plan proposed in plan mode is one of those artificts, not a card that dies with its chat: `exit_plan_mode` files the plan as a Markdown artifict before you are asked to approve it, and refining the plan appends a revision to that same record instead of piling up near-identical copies. The approval card names the record it was filed as and offers **Open in Artificts** for that exact version, so the plan you approved stays readable from any chat about the project and takes requests and comments like any other artifict. Filing is the harness recording the proposal it is already showing you, so it needs no permission prompt; the agent's own `artifict_create` and `artifict_revise` are still refused for as long as plan mode is on. A task with no project folder (or a remote one) keeps the chat-only card, exactly as before.

The default remains ordinary chat: users can send a message and let the agent work without opening this workspace. Comments and preview proposals are editable host-side drafts tied to one version. **Comment** puts you in comment mode: click a point in the preview to pin a comment there, or select text in the preview to quote it. Comments are saved privately against that exact revision and stay private until you include them. **Ask the agent** offers one-click requests about the version on screen — review this design, explore three directions, implement it in the project, set up or check against the design system — each sent like any other studio request; free-form requests go in the chat beside the studio. While a request is outstanding, or after the agent has answered one, a short status names it and its revision — the thread itself is the chat, not a second one. **Send** is the one action that shares the request with the agent: it is recorded against the exact revision and delivered as a normal chat turn, so a working agent is steered and an idle one starts — pause, plan mode, permissions and hooks apply exactly as they do to a typed message. If delivery is refused, the request is withdrawn rather than left looking unanswered. Drafts are kept separately for each exact version while the workspace is open, survive failed saves/sends, and are restored when switching back to that version; closing the workspace discards unsent local drafts. Drafts are not inserted into the transcript or system prompt. The agent revises the artifict and responds to the request (or says it needs clarification); revisions appear in an open editor as they are written, and the prior version stays available for comparison. See the [collaboration smoke-test prompt](collaboration-smoke-test-prompt.md).

Artificts open beside the existing chat/composer, so the preview and the conversation that is about it are the two things on screen and nothing else competes with them. The record surface is **per chat and saved with the chat**: a chat you left on its artificts remembers that, and switching to another chat brings that chat's own answer with it — one chat can be reading a record while another is an ordinary chat. **All artificts** reaches the whole set as a gallery, and the editor expands to take the whole window. Each card marks the format, version count and unresolved request count; the requests themselves span all revisions and label the exact version each one belongs to, so selecting a new version does not erase the prior discussion. Every record and every inline card carries a **Work in progress** notice above its content: an artifict is a draft the agent can still revise, not a finished deliverable or an approval, and when the version on screen is a collaboration record that declares a stage, the notice names that stage as the author's claim rather than a verification result.

**Implement this revision** stages a request naming the exact artifict/revision in the request box. It asks for project inspection, implementation under existing permissions, changed-file links and verification results. It does not send automatically, approve tools, or certify implementation; review it and press **Send**. Selecting text in the host preview offers **Comment on this** (pins a private comment to that text) and **Add to request** (quotes it in the request box). HTML previews retain their bounded marked-target proposal protocol; selections inside isolated frames are not readable by the host. No automatic stage/verification badge is inferred from a pretty preview or an agent response. Screenshot-region targeting, inert SVG/embedded-image thumbnails, and structured implementation/evidence records are supported through the bounded `openleash.collaboration.v1` JSON format. Architecture maps expose component/dependency discussion targets and relative source references; visual investigations expose region proposals, original images and comparisons. See [Artifict collaboration](artifict-collaboration.md) for user steps, agent schema, limits and evidence semantics.

Project artificts are human-readable, repository-controlled data—not trusted instructions or secure/private storage. Reads and shell access are not sandboxed, so an agent can still inspect the checkout directly; never put secrets in artificts. Generated HTML is untrusted code and preview remains subject to the limits in [Security](security-model.md).

## Inline artifict cards

When a visual or structured deliverable materially improves an answer, the agent can choose a temporary `artifict_preview` or a durable `artifict_create` / `artifict_revise`—without asking you to choose a mode. Ordinary chat remains the default; artificts are optional, not a goal to satisfy on every turn. A card appears at its tool call's position in the transcript, before the assistant's final reply. While the tool runs, it shows **Building…**; partial tool JSON and source stay hidden. A preview is attached only after its complete input validates and the tool succeeds.

A **one-off** preview is stored with that chat's transcript, so it appears again when you reopen the same chat. It is never written to `.openleash/artificts/` and is not shared as a project artifict. `artifict_preview` supports HTML, SVG, Markdown, plain text, JSON, and images, with a 240 KiB source limit. A **saved** artifict is stored under the project's `.openleash/artificts/`, remains available across chats, and is also shown inline. Its card distinguishes saved from one-off, offers **Open in Artificts** for that exact saved version, and carries the same round-trip inline: **Ask for a change…** sends a request against that exact version and shows the agent's reply on the card, so a revision can be answered without leaving the conversation. The editor remains the place for versions, comments, pins, captured state and comparison. A collaboration record (`openleash.collaboration.v1` JSON) renders as an explorer in both places rather than as raw source.

On success, inline HTML starts automatically in the existing isolated preview; its **Source** control lets you inspect the completed HTML if you choose. **Expand preview** opens a large host-controlled viewer without restarting the document or losing its live state; **Collapse preview** returns it to the card. Escape closes the viewer when focus is in the host controls (not inside the isolated document). The workspace artifict list can also be hidden to give previews more room. SVG, Markdown, text, images, and JSON are displayed inertly rather than run as active documents, and a collaboration record renders as an explorer rather than as a wall of raw source. Every host-readable kind is drawn in the same framed canvas — its kind, **Preview**/**Source** tabs and **Copy** in one place, with a **Preview width** control (**Full width**, **Tablet**, **Phone**) that frames the artifact on the stage at that width instead of narrowing the frame. The set of records is a gallery you open one record from rather than a list beside it, so a preview is never squeezed into half a column: each card is a 16:10 canvas, and the record the workspace is on is drawn live inside the same isolated runtime while the rest show the picture itself or the document's own first words — one miniature at a time, because each live card is a published document running that artifact's scripts. Narrow windows stack the record against its conversation instead. While the record surface is open the chat rail is forced collapsed (still reachable by hovering the left edge) and the subagent/background rail is hidden, both restored on returning to chat. The workspace takes the larger half of the split, and its **Expand** control gives it the whole window; **Chat** brings the transcript back. When the browser plugin is on, the workspace also carries a **Browser** view beside **Artificts**, so the agent's page opens in that same pane rather than as a dialog over the chat. This is separate from an `openleash-viz` fence in an assistant reply; both are inline chat experiences, but a tool-backed artifict card is produced by a successful artifict tool call. In the Artificts workspace itself, saved HTML still requires an explicit Preview click.

[T3 Code's HTML-render guide](https://github.com/pingdotgg/t3code/blob/main/docs/user/html-renders.md) is a conceptual UX reference for visual replies inside a thread. The guide describes cross-provider inline visual replies separately from MCP Apps—tool-returned iframe UI the current guide says is supported by Codex. [Merged PR #15968](https://github.com/pingdotgg/t3code/pull/15968) describes T3 Code's attachment-based `html_render`. These are inspiration, not a claim of implementation parity: OpenLeash uses its own artifict tools, chat transcript persistence, and isolated preview. See [Security](security-model.md) for its limits.

## Rich visual explanations and inline images

Agents can mix prose with static diagrams, reference pictures, comparison layouts, and interactive teaching demos at the relevant point in a reply. Useful examples include Animator/state graphs, GPU pipeline diagrams, architecture flows, timelines, color sliders, calculators, canvas animations, and searchable tables. Interactive demos use the existing `openleash-viz` runtime; they are not tools and cannot edit files or send answers to the agent.

A closed top-level `openleash-svg` fence renders a complete SVG as a zoomable **image**, without injecting its markup into the host DOM or executing its scripts. Include an SVG namespace, viewBox and a descriptive title. The app's own theme tokens (`--bg`, `--fg`, `--card`, `--accent`, `--chart1`–`--chart6`, the font faces, `--radius`) are defined inside the diagram before it is drawn, so a source written against the tokens keeps the app's colours instead of arriving as an empty black rectangle; a source with literal colours is passed through unchanged. Source and Copy source remain available. Static and interactive blocks share the eight-block/240 KiB limits; unfinished or oversized blocks show a placeholder. Ordinary `svg` fences remain code.

A bare, complete, top-level `<svg>…</svg>` block in an assistant reply is read as that same inert diagram, so a model that writes its diagram without the fence still shows one instead of a wall of escaped XML. The element has to be the whole block: one root `<svg>` element with nothing before or after it, closed, and not split by a blank line — SVG nested inside other raw HTML, opened mid-sentence, or still streaming stays plain text, as does every other kind of raw HTML.

Markdown pictures such as `![Pipeline illustration](https://example.org/image.png "Reference caption")` appear between paragraphs, lazy-load, open in the shared keyboard-accessible lightbox, and show optional captions plus a remote image source link. Failed pictures report an accessible error rather than just a broken icon. Thumbnail and lightbox requests use `no-referrer`. Agents should use discovered public HTTPS image URLs and cite original pages separately; this is not an image-search service. Hosts can still observe requests and IP addresses, URLs may expire, and pictures are not cached for offline use. External pictures belong in Markdown, not in the network-disabled visualization runtime.

Agents show images by path mid-reply, for example a chart or screenshot they just saved: `![Benchmark chart](out/bench.png)` or `![Game view](C:/Users/me/AppData/Local/Temp/shot.png)`. A relative path resolves against the chat's working directory, and an absolute path can point anywhere on this machine's disks. The file must be a real PNG, JPEG, GIF or WebP of at most 8 MiB; both the extension and the file header are checked, so a renamed text file is refused. Paths on another machine's network share (`\\host\share\…`, `//host/…`, `file://host/…`) are refused because opening them makes Windows authenticate to that host; WSL paths are local and allowed. Small inline `data:image/png;base64,…` (or JPEG/GIF/WebP) pictures also render. Other schemes, including `http:`, SVG data URLs and `javascript:`, show as alt text only.

Checkbox totals are document status, not audited completion percentages: old/superseded entries, duplicate IDs, exclusions and nested subtasks may all contribute. A partial inventory should be labeled partial.

Markdown tables with six or more body rows automatically offer a local row filter, matching/total row count, keyboard-accessible sortable column headers, and Reset table. Sorting plain numeric cells is numeric rather than lexical; equal values preserve source order. Filtering and sorting never rewrite the transcript or fetch more data, so they cannot recover missing/truncated rows. Smaller tables retain their plain layout. Failed reply pictures offer Retry image, which remounts the same URL without adding cache-busting/tracking parameters; a broken or expired source may still fail.

## Visual investigation and recovery

Foreground bash tool rows include a collapsible process receipt from actual status/exit metadata, with the command and working directory. Exit zero means process success, **not** that a test suite executed or owner acceptance passed. Unknown, timed-out and interrupted results never become green test claims. Background jobs keep their existing live job-list status; no test-count parser is claimed.

Paused chats offer Recovery context with the last agent step, unfinished todo count/list and live background job IDs. Missing jobs are not presumed running after restart, and todo completion remains a claim rather than evidence. Resume semantics are unchanged.

`web_fetch` includes up to 12 deduplicated HTTPS image candidates from quoted HTML img src/alt attributes, resolved against the fetched page URL. Agents can search for a page then fetch it to discover pictures. This is bounded page extraction, not global image search: lazy-only/srcset/JavaScript images may be missed, remote availability and licenses are unverified, and existing fetch DNS/redirect limitations remain.

A closed `openleash-image` fence accepts JSON with `title`, `src`, optional `after`, and optional `marks` (up to 20 `{x,y,label}` entries with percentage coordinates). Host-rendered numbered markers and a legend annotate the image without changing its bytes. `after` enables a keyboard-adjustable before/after split; originals/source links remain in a disclosure. Match image framing for meaningful comparisons. Supported sources are image file paths (the same rules as Markdown pictures above), HTTPS URLs, or small embedded PNG/JPEG/GIF/WebP data, with the same visual source limits. It is not executable HTML or an agent tool; hosts can observe remote image requests.

Interactive previews offer Compact/Standard/Tall heights and Responsive/Phone/Tablet widths while preserving the current iframe/runtime state. Expansion still offers a larger viewer. Lightboxes focus their close button, trap Tab within controls, retain arrow/Escape navigation, and restore opener focus on close. These have frontend regression coverage; native platform behavior still needs desktop smoke testing.

## Evidence-aware tables and handoffs

Markdown tables with a numeric `Total` column and any of `Implemented`, `Tested`, `Verified`, or `Accepted` get separate labeled progress bars for each stage. This avoids conflating code written with evidence gathered or owner acceptance. Unknown/invalid ratios display a dash; without a total no stage percentage is invented. These are renderings of the supplied counts, **not automated evidence audits**. Ordinary Done/Open tables retain their existing progress column.

Compaction and compacted-fork summaries now request exact verification commands, scope/filter, project copy/working directory, exit codes/counts, evidence paths and the source/version tested. They explicitly preserve unresolved failures, distinguish implementation from owner acceptance, and retain active background IDs, ownership boundaries and pending decisions. The main agent is instructed to cross-check completion claims against observed results and label truncated inventories partial. These are model instructions, not a deterministic claim verifier or a new permission grant.

Static diagrams use their SVG title for their heading/accessibility label and show a readable failure state while keeping Source available if the image cannot render.

## Routers

Settings → Routers decides which model serves a request before the fallback chain runs. A **route** has a name, the models it is the default for (`heads`), an optional catch-all (`all`), an ordered list of fallback `steps`, and what to do when everything is exhausted (`on_exhausted`: `pause` or `fail`). **Rules** sit in front of the chain: each request is described by its situation (who is asking, how large the context is, whether the agent keeps failing the same call, and so on), the rules are checked top to bottom, and the first match picks the model and optionally the effort. Anything it picks still goes through usage caps, account pools, key pools and the pause-when-out behaviour, so a router cannot spend past a cap. The editor has presets, a test panel that runs the same evaluator the harness uses, an activity view of recent decisions, and import/export. Code: `agent/routerules.rs`, `agent/router.rs`, `ui/Routers.tsx`.

## Stats

Settings → Stats shows tokens, cost, time and errors by model, how long the app was open, focused, working and unattended, and a per-chat panel (**Stats…** in the chat menu). A monthly **budget** (default $50; `0` disables it) feeds the budget gate. **Keep chat stats** (on by default) keeps a chat's row after the chat is deleted so totals still add up. **Cache keep-alive** (off by default) sends a small ping every few minutes while a chat is idle so the provider's prompt cache is not evicted, which costs requests and can be set to 2, 4, 8 or 12 pings. Stats are saved to `~/.openleash/stats.json`. Code: `agent/stats.rs`, `ui/Stats.tsx`.

## Phone approvals with ntfy

With remote control on, OpenLeash can send approvals and questions to your phone as [ntfy](https://ntfy.sh) notifications. Each notification links to a confirm page on the remote server; the link carries a one-use grant that expires after 15 minutes and is tied to the session it was issued to. Setup, the topic and the server choice are in [remote.md](remote.md#phone-approvals-with-ntfy).

## Headless CLI and editor server

Two more entry points use the same harness as the desktop app, with no window:

- **`openleash-headless`** runs one prompt to completion and writes NDJSON to stdout (`session`, `assistant`, `tool_call`, `tool_result`, `notice`, `result`). Options: `--prompt`, `--cwd`, `--model`, `--perm` (`disabled`, `allowlist`, `reviewer`, `auto`, `turbo`; default `allowlist`), `--plan`, `--resume <task-id>`, `--timeout-secs` (default 900). Exit codes: `0` done, `1` failed or stopped, `2` usage error, `3` paused, parked or timed out, `4` blocked on an approval or question, which headless mode cannot answer. Build it with `cargo build --locked --bin openleash-headless` inside `src-tauri/`.
- **`openleash-acp`** is an [Agent Client Protocol](https://agentclientprotocol.com) (v1) server over stdio for editors such as Zed, JetBrains, VS Code and Neovim. Approvals are forwarded to the editor as `session/request_permission`, and the sessions run in the `allowlist` mode, so risky tools still ask.

Both binaries are documented in their source headers (`src-tauri/src/headless/main.rs`, `src-tauri/src/acp/main.rs`).

## Tool deferral

Plugin and MCP tools can add a lot of schema to every request. With **Settings → MCP servers → Tool schemas → Defer the long tail to `tool_search`** (`tool_search`, on by default), MCP tool schemas are held back until the agent searches for one. **Also defer plugin tools** (`defer_plugins`, off by default) applies the same rule to GitHub, browser and computer tools, and each MCP server has its own `defer` switch.

## Ultrathread

`/ultra` toggles ultrathread: the main agent can start a tree of nested subagents (`start_ultrathread` asks you to switch on) that keeps working until everything is done. `/ultrawt` does the same with a git worktree per worker, and a final agent merges them back. Nesting depth, the number of running workers and the nudge count are capped in `agent/mod.rs` and `agent/runner.rs`. The layered **ULTRATHREAD X** mode is still hidden (`ULTRA_X_SHOWN` in `ui/Composer.tsx`).

## Commit messages

Agent-made commits get a message from a one-off model call, and the Review page decides what they say about themselves: no attribution, `Co-authored-by:`, `Assisted-by:` or `generated with` trailers. The **run git hooks on agent commits** switch (`git_commit_verify`, off by default) decides whether pre-commit and commit-msg hooks run for those commits. Code: `agent/commitmsg.rs`.

## Welcome tour

New installs open a short welcome tour, which you can reopen from the command palette (**Go to → Welcome tour**). It steps through the main screens with the arrow keys and sets `welcome_seen` once it has been shown.

## Agent tools not covered above

These tools are offered to the model, and each tool's schema describes its arguments. Which agents receive a tool depends on the agent's role and the setting that governs it, as noted in each row.

| Tool | Purpose |
|---|---|
| `list_agents`, `send_message`, `wait` | List the subagents in this task, message one, or wait for reports. |
| `task_status`, `task_resume` | Check a subagent's status, or continue one that stopped. |
| `set_title` | Rename the chat when the task becomes clearer. |
| `web_read_many` | Read up to eight known URLs in parallel. |
| `start_ultrathread` | Ask you to switch the chat into ultrathread. |
| `bisect_edits` | Find the first agent edit that breaks a test command (see below). |

## Needs you inbox and quick navigation

The optional **Needs you** sidebar inbox collects chats blocked on a question or approval so you can jump directly to the pending card. It never answers a question or approves an action on your behalf. The sidebar footer's shortcut button, beside the usage bar, opens Settings → Accounts by default; **Settings → Tabs → Shortcut button** can point it at any settings page. The bookmark shortcut it replaced is gone; saved prompts remain in the sidebar list and new-chat flow.

## Run timeline

**Run timeline…** in a chat's right-click menu, or the Gantt icon in the chat header, shows where that chat's run spent its time and money. The main agent gets one lane, each subagent gets its own lane nested under the agent that launched it, and background commands share a lane at the bottom. Every lane shows each model request attempt (failed attempts are outlined, and retries and fallbacks are marked), each tool call, the retry backoff between attempts, waits on your approvals and questions, pauses, and `wait_for_event` parks. The mouse wheel zooms around the pointer, and Shift+wheel or dragging pans. Hovering a block shows its timing, plus for a model request the model and account, time to first token, tokens, cost and error. Clicking a block jumps to its message or tool row, opening the subagent's panel when the block belongs to a subagent.

Above the lanes is a summary:

- Wall time, split into waiting on you, paused, model, retry, tool and idle. The split is exclusive, so each moment counts once in the first of those that applied on any lane and the parts add up to the wall time.
- Cost by model.
- The slowest tool calls.

The context-window breakdown is not repeated here: **Context window…** opens it in the Details rail. Pause and park blocks end when the chat actually resumes or wakes, not when a subagent or background command finishes while it is held.

Timings are recorded locally and saved with the chat (`Task::spans`, `src-tauri/src/agent/spans.rs`). They hold names, counts, durations and outcomes, never prompts, tool arguments or output. A chat keeps its most recent 6,000 records. Chats from before this feature have no records, so their timeline is estimated from transcript timestamps, drawn dashed, and labelled partial. Gaps over 30 minutes are left out of the estimate. The recorded cost can be lower than the chat's total for the same reason.

## Usage caps

Settings → Accounts draws one bar per usage window a subscription account reports. **Double-click any of those lines** — an account's own, or a provider's aggregated "All 5h" line — to put a cap on it: the harness stops using that account once the window reaches the cap. The aggregated line caps every account of that provider at once, which is what makes the average it draws an average that cannot exceed the cap.

A cap is a standing instruction rather than a bench. Nothing the router does on its own clears one, a resume does not either, and it is stored beside the account, so it survives a restart. **Permanent** stands until you lift it from the same line; **Temporary** lifts by itself after 1, 4 or 24 hours, or when the window rolls over. Either way a cap can be adjusted or removed from the line it stands on.

An active cap is visible in three places. The capped line carries an amber marker where the fill stops once the cap is reached, and a badge naming it — `cap 50%` while it sits ahead of the usage, `capped · 2h 10m` once it is what holds the account back. The account's own state reads **Capped**, and its tooltip names the cap and what lifts it. The sidebar footer's segment turns amber when every account of a provider is held by caps, and its tooltip counts them when only some are. A cap set at or below what a window has already used takes effect immediately, and the dialog says so before it is set.

What a reached cap does is stop using that account. Chats fall through to the other accounts of the kind and then to the rest of their fallback chain, and a chat with nowhere left to go pauses saying so rather than spending the window — it resumes on its own when the cap lifts or the window rolls over, under **Settings → General → Automatically resume when an account is available**. Two things are honest limits: caps act on the provider's own usage reading, refreshed on the same timer as the bars, so a burst that crosses a cap between two reads is reported but not prevented; and a window a provider stops reporting leaves its cap armed and idle rather than applying it to whichever window took its place.

## Spend quota before it resets

Subscription windows are use-it-or-lose-it. **Settings → Accounts → Spend quota before it resets** keeps a backlog of low-priority prompts per project ("sweep TODOs", "audit dependencies") and, when switched on (it is off by default), runs them on quota that would otherwise be forfeited.

Once a minute the watcher looks at the account the router would serve each subscription provider from. When one of its windows resets within **N minutes** (default 30) and at least **H points** (default 20) are still spendable under the ceiling, it starts the oldest matching backlog item as a new chat in its own **git worktree**, pinned to that provider's model with no fallback route. The ceiling of a window is the **Stop at** percentage (default 90% used) or your usage cap on that window, whichever is lower, and it applies to every window of the account: a burn never starts while any window is at its ceiling, so a nearly spent weekly window vetoes burning the 5h one. Only one burner chat runs per provider at a time; it never starts on a stale usage reading, while the provider reports the account as limited, or while everything is paused.

Each item can name a model (which also limits it to that provider) and a permission mode; the default is your default mode, and a stronger mode than your default is held down to it. A burner chat is titled `[burner] …`, opens with a notice saying which account and window it is spending, and is listed under **Started by the burner** in the same settings section.

The run has a hard stop: it is interrupted, with a notice saying why, when the window resets, when any window of the account reaches its ceiling, when the account stops being usable or the router would move to another account, or when the burner is switched off. Send the chat a message to carry on by hand. Usage caps are never exceeded by the burner's own decisions, and the router keeps enforcing them per request. The limit is the one described under usage caps: readings refresh on the account timer and from response headers, so a burst between two readings can overshoot the stop by up to a minute of work. Items that cannot start (not a git repository, SSH project, no model for the provider) stay in the queue with the reason and a **Retry** button.

## Saved prompts and the current project

The Saved prompts screen shows the prompts parked for the folder the app is on. While the sidebar's "show all chats" (`all_projects`) is **off**, prompts saved for another folder are not listed at all — the heading counts only what it lists — and a count of the hidden ones at the bottom of the list reveals them. With it **on**, every prompt is listed and the ones from other folders step back a shade and keep their folder tag; they are two folders' prompts in one list, not two lists, and loading one still switches to that folder as before. Only while it is on does a **Sort** control appear, under the list rather than above it: stored order (oldest first), newest first, by folder with this project's prompts pushed to the bottom, or by prompt text. The choice is saved in settings and still orders a single folder's prompts on a later visit. A prompt with no folder of its own belongs to whichever folder is open, the same rule `loadPrompt` uses.

## Schedules

A schedule sends a prompt to a new agent chat on a timer: **every N minutes or hours**, **daily at a time**, or **weekly on chosen days at a time** (local time). Each run starts a brand-new chat with fresh context, titled **⏰ <schedule name>**, which appears in the sidebar like any other chat. Schedules are stored in `~/.openleash/schedules.json`.

The Schedules screen is hidden by default. Turn on **Settings → Tabs → Show Schedules** to add it to the sidebar beside Saved prompts. Hiding the tab only hides the screen: enabled schedules keep running. To stop them, switch individual schedules off or use **Pause all schedules** on the Schedules screen.

Each schedule has its own project folder, model, effort, workspace (Local or Worktree), plan mode and **permission mode**. The permission mode for a new schedule defaults to your default permission mode, the one new chats use. It can be changed for that schedule without affecting anything else. Runs are unattended, but approvals are never automatic: anything the permission mode would ask about waits in **Needs you** until you answer. With Full Access, the form suggests a worktree so that unattended changes stay on their own branch.

- **Overlap:** if the chat a schedule started last time is still running, the next run is skipped and the skip is recorded.
- **Missed runs:** runs missed while the app was closed are caught up **at most once** when the app starts again, or not at all if **Catch up once if missed while closed** is off for that schedule.
- **Trust:** a schedule whose project folder has no trust decision yet is refused until you open that folder and answer the trust prompt.
- **Run now** fires a schedule immediately. Each row shows the next run, the last result with a link to the chat it started, and a short history.

## Agent memory

Settings → General → **Memory** (on by default) gives the main agent a long-term memory that carries across chats, in the spirit of Hermes Agent's `MEMORY.md` / `USER.md`. Notes come in two scopes:

- **Global** notes about you, such as your role, how you like to work and corrections you gave. They follow you into every project and live in `~/.openleash/memory/_global/`.
- **Project** notes cover ongoing work, decisions and deadlines that aren't in the code, and where things live outside the repo. They live in `~/.openleash/memory/<project>-<fingerprint>/`, shared by every worktree of the same repository.

Each scope is a `MEMORY.md` index plus one small markdown file per note. When a chat starts, both indexes are rendered into its system prompt under **What you remember**. This is a frozen snapshot, so the prompt cache holds, and a note saved mid-chat loads in the next chat.

The agent saves on its own. It uses the `memory` tool to `save` new notes, `update` notes that changed instead of duplicating them, `forget` notes that are stale, and `recall` a note's detail. It is told not to store secrets or anything a `grep` would find again. A note is framed as the agent's own earlier writing, never as your instructions: when one conflicts with what you say now, you win. Writes refuse invisible and control characters (zero-width, bidi overrides, Unicode tag characters), and a hand-edited index line containing one is not loaded. Each index is capped at 200 lines or 25 KB.

Everything is plain markdown that you can read, edit or delete by hand. Switching Memory off removes the tool's effect and the snapshot from new chats; nothing on disk is deleted. Builds before this one shipped memory off by default and wrote that default into every settings file, so the first launch of this build turns it on once. A later "off" sticks.

## Save a chat as a skill

Right-click a chat in the sidebar (or open the command palette in a chat) and choose **Save as skill…** to turn what the chat worked out into a reusable Agent Skill (`SKILL.md`). Nothing runs until you click **Draft skill**: a one-off model call (the chat's own model by default, or one you pick) reads the conversation and writes a draft with a `name`, a one-line `description` that says when to use it, and a body covering prerequisites, the steps that worked, exact commands, pitfalls discovered along the way and how to verify the result. The call is billed like a summary and does not change the chat.

The draft opens in an editable preview. Edit the name, description and body, then choose where it goes:

- **Global** — `~/.openleash/skills/<name>/SKILL.md`, available in every project.
- **This project** — `<project>/.openleash/skills/<name>/SKILL.md`, which you can commit. Project skills only load once the folder is trusted, and remote (SSH) projects can only save globally.

Saving checks the result before anything is written. The name must be a safe folder name (lowercase letters, digits and dashes, at most 64 characters, no leading or trailing dash, not a Windows device name such as `con`). The description is collapsed onto one line, so it cannot add frontmatter keys. Invisible and control characters are refused, as they are for memory. An existing skill with the same name is never replaced without your confirmation, and replacing it rewrites only its `SKILL.md`; other files in that folder stay. API-key-looking strings (provider keys, GitHub/Slack/AWS/Google tokens, bearer tokens, JWTs, private keys and `password=` style values) are replaced with `<REDACTED>` in the draft. If anything that looks like a secret is still there when you save, you are asked to confirm first. Detection is heuristic, so read the draft before saving. The saved skill is switched on and appears in the skills list for new chats. Chats that are already open keep their frozen prompt.

**Only you can start this.** A skill is loaded into later chats, so agents get no tool, slash command or prompt text that creates one, and Discord and other connector messages cannot trigger it. The commands only answer the app's main window, and they refuse while an agent is controlling the desktop. Remote control in a paired browser runs the same app UI, so it counts as you.

## Agents seeing and messaging your other chats

Settings → Chats → **Other chats** (on by default; switch it off to stop this) lets a chat's main agent work across conversations instead of asking you what else is open. `list_chats` searches your chats and reports what each one is doing right now — running, waiting on you, paused, waiting on a trigger, done, stopped, idle — with its current step, project, branch, running subagent count and how long ago you last used it, matching the status words the sidebar and command palette use. `message_chat` sends one of them a message by id or title.

## Finding the edit that broke it (checkpoint bisect)

With checkpoints on (Settings → Checks & hooks, the default), every successful `edit_file`, `multi_edit` and `write_file` is also kept as a snapshot of its own in the chat's shadow checkpoint store, so the file state after *each* agent edit can be reconstructed — not only the state at the end of each turn. Review → **Find breaking edit…** takes a test command that exits 0 when things are good, an optional range of steps (default: the whole chat), a per-run timeout, runs per step (2–3 detects flaky results) and optional shared folders. It binary-searches the chat's edit history and reports the first bad step: the tool call, the file, its diff, with **Jump to message** and **Revert this file** (the existing per-file revert, which restores the file to before the agent first touched it — later edits to that file go too). Progress streams live and the run can be cancelled. Agents get the same capability as the `bisect_edits` tool.

- **Isolation.** Each probed state is written into a fresh scratch folder under the system temp directory and the command runs there; the scratch folder is deleted afterwards, also on timeout or cancel. Your working tree, its `.git` and the checkpoint store's own index/HEAD are not touched.
- **Ignored folders.** A scratch copy holds only what a checkpoint holds: git-ignored folders such as `node_modules` or `target` are missing, so a command that needs them fails everywhere (reported as "already fails before the first step"). Name them under *shared folders* to link them into each copy (a junction on Windows). That is opt-in and read-through: a command **can write through the link** into your real folder; cleanup unlinks before deleting, so the folder itself is never removed.
- **Steps.** Most steps are agent edits. When files changed between two edits by something else — a shell command, you, a rewind — that difference becomes an `external` step of its own, so a break from `npm install` is not blamed on the next edit.
- **Timeouts and flaky results** make a step unclassifiable rather than bad; if they leave the answer ambiguous you get the list of candidate steps instead of a guess.
- **Permissions.** The command goes through exactly the checks `bash` does: deny rules, allow rules, plan mode, the permission rung, the chaining/substitution guard, the env-file guard, subagent read-only/no-shell/fileRegex limits, and `bash` pre-tool hooks for the agent tool. From Review, any *deny* refuses it; an approval prompt is answered by the confirmation dialog, which shows the exact command. One bisect runs per chat at a time.
- **Not available** for SSH projects (no local checkpoints), docker workspaces (`bash` runs in the container there; running the command on the host instead would be a different boundary) or with checkpoints off. Edits made inside a subagent's own isolated worktree are not recorded. A rewind drops the abandoned turns' steps.

## HTTP requests

`http_request` lets the agent make one HTTP request of its own choosing: call an API, check an endpoint on a local dev server, or fire a webhook. It is not for reading documentation or web pages (that is `web_fetch`) or for GitHub (the GitHub plugin).

- **Inputs:** `method` (`GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`), `url` (`http`/`https` only; a URL with `user:pass@` in it is refused, so credentials go in headers), `headers` (string values; `Host`, `Content-Length`, `Transfer-Encoding`, `Connection` and the other hop-by-hop headers are refused), and either `body` (a string) or `json` (any JSON value, which sets `content-type: application/json` unless you set one), not both. `timeout_ms` defaults to 30,000 and is capped at 60,000; `max_bytes` caps the download at 1 MiB by default and 10 MiB at most; `follow_redirects` is on by default, for at most 5 hops.
- **Result:** the status line, the final URL if the request was redirected, a selected set of response headers (`content-type`, `content-length`, `location`, `etag`, `last-modified`, `cache-control`, `retry-after`, `allow`, `www-authenticate`, `link`, `x-request-id` and rate-limit headers, with `set-cookie` values redacted), then the body: JSON pretty-printed, text as text, and binary summarized as its size and content type. `HEAD` has no body. A body cut off at `max_bytes` says so explicitly, and output longer than the tool-output cap is cut to its head and tail with the full text saved to a spill file, as `bash` output is.
- **Approval:** a `GET` or `HEAD` to a public host runs without asking, like `web_fetch`. Any other method asks (Full Access runs it), and a request to this machine or the private network asks at every level, including Full Access. Cloud metadata and link-local addresses are always refused. The approval card is titled like **HTTP POST api.example.com** and shows the method, URL, headers and a body preview with secrets redacted, plus why it is asking: the request writes data, reaches a local service on this machine, or reaches the private network. **Always allow** records an exact rule such as `http_request:POST https://api.example.com:443` (or `http_request:POST http://localhost:3000`): the method, scheme, host and effective port are all part of the rule. HTTPS :443 cannot authorize HTTP :80. No wildcard allow is honored. Deny rules such as `!http_request`, `!http_request:DELETE *` or `!http_request:* api.example.com` refuse matching calls, and a deny wins over everything.
- **Where it runs:** plan mode allows `GET`/`HEAD` (asking for local or private targets) and refuses other methods. Read-only subagents only get `GET`/`HEAD`; other subagents get every method through the same gate. The tool is not exposed over MCP. In an SSH project the request is still made from this computer, so `localhost` means your machine, not the SSH host.

What it reaches, how redirects and DNS are checked, and what redaction does and does not cover: [Security](security-model.md#http-requests). Code: `src-tauri/src/agent/http_tool.rs` (execution, classification, redaction) and the `http_request` arm in `src-tauri/src/agent/permissions.rs`.

## Code intelligence (`lsp`)

Agents can ask the project's language server instead of grepping: `definition`, `type_definition`, `implementation`, `references`, `hover`, `document_symbols`, `workspace_symbols`, `diagnostics`, and `incoming_calls` / `outgoing_calls` (the call hierarchy). A position is a 1-based `line` plus either the `symbol` on that line (preferred, since models miscount columns) or a 1-based `character`. Results come back as `path:line:col` with the source line, grouped and capped so a busy symbol cannot flood the context.

The server is picked by file extension: rust-analyzer for Rust, typescript-language-server for TS/JS, pyright (then basedpyright, then pylsp) for Python, gopls for Go, clangd for C/C++. It must be installed on your `PATH`; if it is missing the agent is told how to install it. The workspace root is found from the nearest `Cargo.toml` (the topmost one, so a Cargo workspace is indexed once), `tsconfig.json`/`package.json`, `pyproject.toml`, `go.mod` or `compile_commands.json`, never above the project. One server per root is shared by every chat and subagent, waits for its first index before answering (and says so if it is still indexing), picks up the agent's edits from disk on each call, and shuts down after 15 idle minutes. Starting a server asks for approval except on Full access, with a per-server "always" rule: see [Security](security-model.md#security-model). Not available for SSH or WSL projects yet. Code: `agent/lsp.rs`.

## Waiting on events

`wait_for_event` parks a chat until something happens, then starts a follow-up turn on its own, so the agent never spends requests polling. Besides `timer`, `ci` and `pr`, a chat can wait on:

- **`file`**: a file or folder (recursive, honouring `.gitignore`) being created, changed or deleted, such as a build artifact or a report.
- **`job`**: one of the chat's own background commands exiting, or, with `match`, printing a line that matches a regex (`ready|listening on`). The matching line is handed back to the agent. Watching never moves the agent's own `bash_output` cursor.
- **`chat`**: another chat (by id or title, needs **Other chats** on) stopping work, whether it finishes, stops, pauses, parks or needs its user.

Any source except `timer` takes `timeout_s`, which wakes the chat anyway if the trigger never fires. Local triggers are checked every two seconds. As before, sending a message, Stop, or Resume clears the park, and a park does not survive an app restart.

for that site. Settings → Plugins → Browser offers an interaction default and

are reachable; private-network hosts need approval and metadata/link-local targets
are blocked. Page content remains untrusted data. See [Security](security-model.md#browser-plugin).

By default each task uses a throwaway profile. **Keep sign-ins between chats**
opts into OpenLeash's separate persistent profile, so the agent can act as you on
sites you sign into through the shared view. **Show browser window** makes that
browser visible. Download folder, viewport and Developer mode are configured in
[Settings](configuration.md#browser).

### Shared Browser view

Open **Artificts** in the chat header, then **Browser**, or use **Open Browser
view** on a browser tool row. This is a shared screenshot view of the main
agent's browser, not a remote page embedded into the privileged app webview.
The tab strip supports new/switch/close; the address bar has keyboard-searchable
session history (addresses only, never a search-engine query), back/forward and
reload. Click the live view, then type or scroll while it has focus. Dialogs have
an explicit Accept/Dismiss banner. The activity line shows when the agent is
using the same browser. Expand the pane for more room.

**Annotate** lets you click an element or drag a region, write a comment, and
optionally adjust font, spacing and colours with a live inline-style preview.
Collect up to ten notes, then **Send to agent** delivers them as an ordinary chat
turn with element refs/selectors, bounding boxes, requested styles, an overview
and cropped screenshots. Draft notes are not sent until you press Send. Previews
are not saved to source; the agent makes the real fix in project files under the
chat's normal permissions. Discard reverts the previews. Your direct clicks,
typing and dialog answers act immediately on the site, so coordinate with an
agent that is using the browser at the same time.

## Interactive inline visualizations

Assistant replies can include a self-contained HTML/CSS/JavaScript block in an exact, closed, top-level `openleash-viz` fence. Once the fence is complete, it renders inline and runs automatically—there is no Preview step. While that block is still streaming, the card shows a friendly **Working on the interactive preview…** placeholder rather than exposing the unfinished source. **Source** is the control for users who choose to inspect the code. The assistant can still include normal inline text and ordinary code fences before or after a visualization; only exact, closed `openleash-viz` fences in assistant replies execute. Ordinary HTML/other fences, raw HTML, user messages, approvals, and tool details remain inert; the one exception is a bare, complete, top-level `<svg>…</svg>` block, which renders as the same inert diagram image an `openleash-svg` fence produces. Saved HTML documents in the separate project Artificts workspace still need an explicit Preview click. These chat visualizations are full local JavaScript interactions (charts, calculators, diagrams, and demos); external libraries and resources cannot be loaded, with one exception: the bundled chart engine described below.

Keep visualizations purposeful, self-contained, accessible, and responsive. An inline chat visualization offers **Source**, **Copy source**, **Expand preview**, and **Stop** controls. Expansion preserves the current iframe and its interactive state; it does not publish another document. If automatic publication fails because the bounded renderer registry is full, Source remains available and Retry preview can try again. Theme tokens are `--bg`, `--fg`, `--card`, `--muted`, `--accent`, `--primary`, `--border`, `--chart1`–`--chart6`, `--font-sans`, `--font-mono`, and `--radius`. `--font-sans` and `--font-mono` carry the app's own faces, so a document that names no family — and every `<text>` in an `openleash-svg` diagram, which has no host CSS of its own — renders in the app's face rather than the platform's default serif. Reopening a transcript can render a visualization again; it does not restore the prior live runtime. Up to eight visualizations per reply qualify, each with at most 240 KiB of source; empty, oversized, excess, or unfinished exact-tagged blocks show a non-code placeholder with an optional Source disclosure. Published documents live only in bounded process memory (64 documents / 8 MiB total, 30-minute expiry), not files.

### Charts and graphs

For data charts, an assistant can write an exact, closed, top-level `openleash-chart` fence holding one JSON object: an [Apache ECharts](https://echarts.apache.org/en/option.html) 6 option. The app bundles ECharts and renders the option inside the same isolated preview frame, so the agent controls the whole option surface — dozens of series types (line, bar, scatter, pie, radar, heatmap, candlestick, boxplot, treemap, sunburst, sankey, force graphs, trees, funnels, gauges, parallel coordinates, calendars, polar), datasets and transforms, multiple axes and grids, zoom/brush, visual maps, mark lines/areas, rich-text labels, and animation. Charts follow the app theme (`--chart1`–`--chart6`, text, border and card colours, the app's font) unless the spec sets its own colours. An optional top-level `"openleash": {"height": 560, "renderer": "svg", "title": "…"}` sets the frame height (200–1200 px), renderer and card title; it is removed before the option is applied. **Source** shows the JSON spec rather than the generated page. A spec that is not a JSON object shows its error and Source instead of a chart. Chart fences share the eight-blocks-per-reply and 240 KiB limits with other visual blocks. JSON cannot carry functions, so formatters use ECharts string templates; the sandbox cannot download, so `toolbox.saveAsImage` does nothing.

When a chart needs code — callback formatters, custom series, generated data, linked charts or custom controls — an `openleash-viz` document can load the same engine with `<script src="lib/echarts.js"></script>`. That relative path is the only external script a visualization document may load; `echarts.init(el)` applies the app theme unless another theme is passed. No map data is bundled. Because saved HTML artificts run in the same frame they can load it too, but an exported copy of such an artifict does not include the engine.

Automatic JavaScript execution in chat increases exposure: model-generated code starts running as soon as its exact fence is complete. The iframe uses a separate visualization origin and strict sandbox/CSP controls; it has no network, filesystem, native IPC, or app/message bridge. These controls reduce capabilities but do not make generated code trustworthy or resource-safe. There is no per-visualization CPU, memory, or execution-time budget: a loop or allocation can consume CPU/memory or hang the webview, and Stop may not recover an already blocked renderer. Do not include secrets or sensitive data in a visualization or enter them into its UI. See [Security](security-model.md) for implementation details and platform-specific caveats; native webview behavior is not guaranteed uniformly across platforms.
